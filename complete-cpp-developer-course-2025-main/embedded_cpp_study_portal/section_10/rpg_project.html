Section 10 ⚡ Embedded Relevance: High Class Hierarchies Factory Pattern Virtual Destructors Memory Leaks & Cleanup Static Object Pools

OOP Class Hierarchies, Factory Pattern, and Safe Embedded Memory Management

Executive Summary: A complete multi-class RPG character architecture demonstrating member initializer lists, virtual destructors, factory instantiation, and container ownership. We analyze the risks of raw pointer collections (std::vector<Player*>) in safety-critical systems and demonstrate zero-heap static object pooling compliant with AUTOSAR A18-5-2.

#include <vector>

int main() {
    int choice;
    int raceNum;
    string playerName;
    
    // Vector of raw owning pointers
    // ⚠️ EMBEDDED CONCERN: Raw pointer vectors require manual lifecycle management.
    // In C++11/14, `vector<unique_ptr<Player>>` or static object pool is mandatory.
    vector<Player*> playerList;

    printMainMenu();
    cin >> choice; 
    cin.get(); // Consume trailing newline

    while (choice != 0) {
        cout << "What would you like to name your character?" << endl;
        getline(cin, playerName);

        printRaceMenu();
        cin >> raceNum;
        cin.get();

        // Factory instantiation returning raw heap pointer
        Player* tempPlayer = createPlayer(playerName, choice, raceNum);
        if (tempPlayer != nullptr) {
            playerList.push_back(tempPlayer);
        }

        printMainMenu();
        cin >> choice;
        cin.get();
    }

    printAll(playerList);
    
    // Explicit manual deallocation
    doCleanup(playerList);

    cout << "Program done!" << endl;
    return 0;
}

Race getRace(int raceNum) {
    switch (raceNum) {
        case 1: return Race::HUMAN;
        case 2: return Race::ELF;
        case 3: return Race::DWARF;
        case 4: return Race::ORC;
        case 5: return Race::TROLL;

// Factory Function: Centralizes object construction
Player* createPlayer(string name, int typeNum, int raceNum) {
    Race race = getRace(raceNum);
    switch (typeNum) {
        case 1: return new Warrior(name, race);
        case 2: return new Priest(name, race);
        case 3: return new Mage(name, race);
        default: return nullptr;
    }
}

// Polymorphic output loop passing container by const-reference
void printAll(const vector<Player*>& playerList) {
    for (const Player* player : playerList) {
        cout << "My name is " << player->getName()
             << ". I'm a " << player->whatRace()
             << " and my attack is: " << player->attack() << endl;
    }
}

// Manual memory reclamation
void doCleanup(vector<Player*>& playerList) {
    for (Player* player : playerList) {
        delete player; // Calls virtual destructor safely
    }
    playerList.clear();
}

📚 2. Core C++ Concepts Deep-Dive

1. Member Initializer Lists vs Body Assignment

In Player.cpp, the constructor uses a Member Initializer List:

Player::Player(string name, Race race, int hp, int mp) 
    : name(name), race(race), hitPoints(hp), magicPoints(mp) {}

This avoids default-constructing the member variables first and then re-assigning them in the constructor body, saving redundant destructor and assignment operations.

2. Proper Virtual Destructor Idiom

Because Player defines virtual ~Player() = default;, calling delete player; in doCleanup() accurately invokes the specialized destructor of Warrior, Priest, or Mage before reclaiming base storage.

⚡ 3. Embedded Systems & Hardware Reality

1. The Danger of Dynamic Heap Operations in Safety-Critical Firmware

  • Heap Fragmentation: Repeated new and delete cycles inside dynamic menus create memory "holes" in embedded SRAM. Eventually, a future allocation fails even though total free memory appears sufficient.
  • AUTOSAR A18-5-2 Violation: In automotive ECUs (ISO 26262 ASIL D), dynamic memory allocation is strictly prohibited after the initial startup boot phase.

2. Static Object Pooling (Zero-Heap Embedded Alternative)

Instead of heap-allocating players dynamically, embedded developers use Pre-Allocated Static Pools or std::variant arrays bounded at compile time.

💡 4. Embedded Refactoring: Static Object Pool with `std::variant`

Here is an embedded refactoring using std::variant and std::array that requires ZERO heap allocations and ZERO vtable overhead:

#include <iostream>
#include <array>
#include <variant>
#include <string_view>

struct Warrior {
    std::string_view name;
    constexpr std::string_view attack() const { return "Sword Strike!"; }
};

struct Mage {
    std::string_view name;
    constexpr std::string_view attack() const { return "Arcane Blast!"; }
};

// Type-safe zero-heap polymorphic union
using PlayerEntity = std::variant<Warrior, Mage>;

int main() {
    // Fixed compile-time bounded buffer in SRAM
    constexpr size_t MAX_ENTITIES = 2;
    std::array<PlayerEntity, MAX_ENTITIES> staticWorld = {
        Warrior{"Thor"},
        Mage{"Gandalf"}
    };

    // Pattern matching visitor dispatch
    for (const auto& entity : staticWorld) {
        std::visit([](const auto& player) {
            std::cout << player.name << ": " << player.attack() << '\n';
        }, entity);
    }

    return 0;
}

📝 Knowledge Verification Quiz

Test your knowledge on OOP ownership, destructors, and embedded memory constraints.

Q1. Why is virtual ~Player() = default; critical when managing std::vector<Player*>?
A It forces the vector to pre-allocate capacity automatically.
B It ensures that executing delete player calls the derived class destructor (e.g. ~Warrior) to clean up all derived resources.
C It prevents the object from being copied by value.
D It moves the object storage to Flash ROM.
Detailed Explanation: Option B is correct. When an object is deleted via a base pointer (Player*), a virtual destructor guarantees runtime polymorphic dispatch to the actual derived destructor, preventing memory leaks and resource corruption.
Q2. According to safety standards like AUTOSAR and MISRA C++, why is dynamic allocation (new/delete) inside cyclic loops prohibited in automotive ECUs?
A The CPU halts permanently whenever new is invoked.
B C++ compilers do not support pointers on ARM Cortex microcontrollers.
C Dynamic heap allocation leads to SRAM fragmentation and non-deterministic execution timing, risking deadline misses.
D Vectors cannot store pointers to derived classes.
Detailed Explanation: Option C is correct. The heap allocator (malloc/free) has non-deterministic runtime latency and causes heap fragmentation over long operational lifespans, which can trigger catastrophic Out-Of-Memory (OOM) faults.
Q3. In modern C++ (C++17), what zero-heap abstraction replaces polymorphic base class pointers without dynamic memory?
A std::variant combined with std::visit stored in a fixed std::array.
B std::shared_ptr.
C malloc with void* casts.
D Global raw pointers.
Detailed Explanation: Option A is correct. std::variant implements a type-safe tagged union stored directly on the stack or in static memory. When combined with std::visit, it provides polymorphic behavior with zero dynamic allocation.
